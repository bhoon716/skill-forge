# Cognitive Debt

## 目的

找出让代码行为和设计意图难以发现、解释、测试或安全修改的代码库条件。本 Skill 所说的**代码库认知负债**，是实现与对其工作方式和原因的、有证据支持的共同解释之间可能存在的差距。

仓库证据可以揭示理解风险，却无法测量个人或团队实际理解了什么。把代码异味当成待调查的信号，而不是负债本身的证明。代码是否由 AI 编写、文件长度、抽象数量和复杂度指标本身都不能证明代码有问题。

## 适用场景

- 用户要求审查代码库或子系统中累积的复杂性、代码理解问题或认知负债。
- 用户希望发现并排序重复业务规则、多个事实来源、隐藏耦合、意图不清、不必要的间接调用、已证实的死代码，或不必要的依赖与基础设施增长。
- 用户要求在一条代码路径或整个代码库中降低这些问题，而不是执行一个已明确指定的局部清理。

## 不适用场景

- 用户已指定一个保持行为的具体 cleanup：使用 `refactoring`。
- 现有行为已损坏：使用 `bugfix`。
- 任务要添加能力或产品行为：使用 `feature-dev`。
- 用户要求有意改变架构或 contract：先用 `architecture` 评估决策。
- 用户只是询问 cognitive debt 的含义：直接解释。

## 审计流程

### 1. 限定范围

遵循用户指定的子系统、流程或关注点。范围较广时，先检查有代表性的用户路径、近期变动频繁的区域或最相关模块；除非用户要求并且确实完成，否则不要声称审计了整个仓库。说明检查了什么以及哪些内容未检查。

### 2. 追踪实现

读取适用的仓库指令，以及完成任务所需的架构说明、入口、manifest、测试和配置。至少追踪一条代表性路径，覆盖调用方、数据或状态所有权、副作用和测试。在历史记录有助于确认意图或反复修复时查看版本历史。验证实际 import 和调用；目录名不能证明模块边界。

### 3. 调查候选信号

查找以下证据：

- 同一业务规则或策略在多个位置实现，或存在多个看似权威的数据来源。
- 通过共享状态、数据库、配置或副作用产生的隐藏耦合。
- 遮蔽而非澄清行为的调用链、wrapper 或概念。
- 可以证明已不再使用的代码或过时 scaffolding。
- 缺乏实际需要依据却增加的依赖、服务、队列、配置层或基础设施。
- 名称或文档与代码和测试显示的行为相矛盾。
- 无法从现有代码、测试、历史或项目文档确认的重要设计意图。

不要仅因某种模式看起来奇怪就将其计为负债。检查它是否用于保护领域不变量、兼容性边界、安全属性、可靠性要求、经过测量的性能需求或既有项目惯例。判断代码未使用前，考虑 dynamic dispatch、plugin、reflection、生成代码和仓库外部的使用方。

### 4. 根据证据和影响排序

区分观察与解释。每个 finding 都要说明：

- **位置：** 精确文件、symbol 和相关调用路径。
- **证据：** 代码、测试、配置或历史记录具体显示了什么。
- **理解风险：** 哪些行为难以发现或推理，涉及什么变更或故障场景。
- **信心与影响：** 用简短理由给出高、中或低判断；不要编造数字分数。
- **最小有效后续步骤：** 范围有限的修改、需要确认意图的问题，或复杂性合理时保持不变。

优先处理影响多条流程或每次变更都会重现的风险，同时考虑修复成本和风险。如果 diff 看起来整洁却隐藏了行为或增加了概念，就不算成功。

审计报告包括检查范围、简短流程图、排序后的 findings、合理存在的复杂性和未解决问题。若用户只要求诊断，则保持只读。

## 降低负债的流程

用户要求降低已识别的问题时，只修改审计中有证据支持的内容：

1. 选择一个行为和所有权均可确认、范围有限的 finding。
2. 明确必须保持的不变量，找出覆盖它的测试或等价检查，并在编辑前运行 baseline。
3. 依次判断代码能否安全删除、与现有实现合并，或确实需要新增内容。这只是判断辅助，不代表必须删代码或避免有用的抽象。
4. 每次只做一个小改动。只有解决了已证实的复杂性或明确约束时才添加 abstraction、dependency、service 或 infrastructure；不要为假设的未来需求添加。
5. 每次修改后重新运行同一组相关检查，检查 diff 中的行为变化和过时代码。如果证据不再支持修改，就停止或回滚。
6. 报告改动、修改前后的检查结果、剩余不确定性，以及留待单独决策的 finding。

不要以 cleanup 为名悄悄改变产品行为、public contract、数据 schema、权限、安全、隐私、计费或部署拓扑。若修复需要这类变化，说明证据和所需决策，然后转到 `architecture` 做设计评估或询问用户。发现功能 bug 时，报告问题或改用 `bugfix`，不要混入 cleanup。

## 理解交接

结束时简要解释追踪到的行为及证据确认的原因。无法确认的意图标为未知，不要自行编造。生成的流程图或摘要可以降低查阅难度，但不能证明团队已恢复共同理解。只有用户要求，或需要记录经过验证且稳定的决策时，才创建或更新持久文档。

## 停止条件

当请求的审计已有基于证据排序的 findings 和清晰的范围限制，或请求的范围内修改已验证时停止。如果下一步依赖未解决的产品意图、有风险的 contract 或架构选择、或缺乏依据的假设，就不要继续扩大范围；明确报告需要做出的决定。

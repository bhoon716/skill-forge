# Cognitive Debt

## 목적

코드의 동작과 설계 의도를 찾고, 설명하고, 테스트하고, 안전하게 바꾸기 어렵게 만드는 저장소의 조건을 찾는다. 이 스킬에서 **코드베이스 인지부채**는 구현과 그 동작 방식·이유에 대한 근거 있는 공동 설명 사이의 잠재적 간극을 뜻한다.

저장소 근거로 이해 위험은 찾을 수 있지만 사람이나 팀이 실제로 무엇을 이해하는지는 측정할 수 없다. 코드 냄새는 조사할 신호이지 부채의 증거 자체가 아니다. AI가 작성했는지, 파일이 긴지, abstraction 이 많은지, 복잡도 수치가 어떤지만으로 문제라고 판단하지 않는다.

## 이 스킬을 사용할 때

- 누적된 복잡성, 코드 이해, 인지부채에 초점을 둔 코드베이스 또는 하위 시스템 감사를 요청할 때.
- 중복 비즈니스 규칙, 여러 개의 진실 공급원, 숨은 결합, 불분명한 의도, 불필요한 간접 호출, 입증된 dead code, 불필요한 의존성·인프라 증가를 찾고 우선순위를 정할 때.
- 이미 정해진 국소 정리 하나가 아니라 코드 경로나 저장소 전반에서 이런 문제를 줄여 달라고 할 때.

## 이 스킬을 사용하지 않을 때

- 동작 보존 cleanup 범위가 구체적으로 정해져 있을 때는 `refactoring`을 사용한다.
- 기존 동작이 깨졌을 때는 `bugfix`를 사용한다.
- 기능이나 제품 동작을 추가할 때는 `feature-dev`를 사용한다.
- 의도적인 아키텍처 또는 contract 변경을 요청할 때는 먼저 `architecture`로 결정을 검토한다.
- 인지부채가 무슨 뜻인지 묻기만 하면 바로 설명한다.

## 감사 워크플로

### 1. 범위 제한

사용자가 지정한 하위 시스템, 흐름, 관심사를 기준으로 한다. 범위가 넓으면 대표적인 사용자 흐름, 최근 변경이 잦은 영역, 요청과 관련성이 높은 모듈부터 본다. 요청하고 실제로 완료한 경우가 아니면 저장소 전체를 빠짐없이 감사했다고 말하지 않는다. 무엇을 살폈고 무엇은 살피지 않았는지 밝힌다.

### 2. 구현 흐름 추적

적용 가능한 저장소 지침과 필요한 만큼의 아키텍처 문서, 진입점, manifest, 테스트, 설정을 확인한다. 대표 경로 하나 이상에 대해 호출자, 데이터나 상태 소유권, side effect, 테스트까지 추적한다. 의도를 밝히거나 반복된 수정 흔적을 찾는 데 도움이 될 때 버전 이력을 본다. 디렉터리명만으로 모듈 경계를 추정하지 말고 실제 import와 호출을 확인한다.

### 3. 후보 신호 조사

다음 근거를 살핀다.

- 같은 비즈니스 규칙이나 정책이 여러 곳에 구현되어 있거나 진실 공급원이 여러 개로 보임.
- 공유 상태, 데이터베이스, 설정, side effect를 통한 숨은 결합.
- 동작을 명확히 하기보다 가리는 호출 체인, wrapper, 개념.
- 사용되지 않음을 입증할 수 있는 코드나 오래된 scaffolding.
- 확인된 필요 없이 추가된 의존성, 서비스, queue, 설정 계층, 인프라.
- 코드와 테스트가 보여 주는 실제 동작과 이름 또는 문서가 충돌함.
- 기존 코드, 테스트, 이력, 프로젝트 문서로 중요한 설계 의도를 확인할 수 없음.

낯설어 보인다는 이유만으로 부채로 세지 않는다. 도메인 불변조건, 호환성 경계, 보안 속성, 안정성 요건, 측정된 성능 요구, 기존 프로젝트 관례를 지키기 위한 복잡성인지 확인한다. 사용하지 않는 코드로 판단하기 전 dynamic dispatch, plugin, reflection, generated code, 저장소 외부 consumer도 고려한다.

### 4. 근거와 영향에 따라 우선순위화

관찰과 해석을 분리한다. 각 finding에 다음을 적는다.

- **위치:** 정확한 파일, symbol, 관련 호출 경로.
- **근거:** 코드, 테스트, 설정, 이력에서 확인한 내용.
- **이해 위험:** 어떤 동작이나 변경·장애 상황에서 무엇을 파악하기 어려운지.
- **확신도와 영향:** 짧은 이유와 함께 높음·중간·낮음으로 판단하고 숫자 점수는 만들지 않는다.
- **가장 작은 다음 단계:** 범위가 제한된 변경, 확인이 필요한 의도 질문, 또는 복잡성이 정당화되면 변경 없음.

여러 흐름에 걸치거나 변경 때마다 반복되는 위험을 우선하되, 수정 비용과 위험도 함께 고려한다. 행동을 숨기거나 개념을 더 보태는 깔끔한 diff 는 성공 기준이 아니다.

감사 결과에는 확인 범위, 간단한 흐름도, 우선순위가 있는 finding, 정당한 복잡성, 미해결 질문을 포함한다. 진단만 요청했다면 읽기 전용으로 진행한다.

## 감소 워크플로

사용자가 확인된 부채를 줄여 달라고 하면 감사에서 근거가 확인된 항목만 변경한다.

1. 동작과 소유권을 파악할 수 있는 범위가 제한된 finding 을 고른다.
2. 보존할 불변조건을 밝히고 이를 보호하는 테스트나 동등한 검사를 찾는다. 편집 전에 baseline 을 실행한다.
3. 코드를 안전하게 삭제할 수 있는지, 기존 구현과 통합할 수 있는지, 새로운 것이 필요한지 순서대로 검토한다. 이는 판단 보조일 뿐 코드를 삭제하거나 쓸모 있는 abstraction 을 피하라는 규칙이 아니다.
4. 한 번에 작은 변경 하나만 한다. 입증된 복잡성이나 명시된 제약을 해결할 때만 abstraction, dependency, service, infrastructure 를 추가한다. 가상의 미래 필요를 위해 추가하지 않는다.
5. 각 변경 뒤 같은 관련 검사를 다시 실행하고 diff 의 동작 변경과 오래된 코드를 살핀다. 근거가 약해지면 중단하거나 되돌린다.
6. 변경 내용, 편집 전후 검사 결과, 남은 불확실성, 별도 결정으로 남긴 finding 을 보고한다.

제품 동작, public contract, 데이터 schema, permission, security, privacy, billing, deployment topology를 cleanup이라는 이름으로 조용히 바꾸지 않는다. 줄이려는 문제가 이런 변경을 필요로 하면 근거와 필요한 결정을 설명한 뒤 `architecture`로 설계 검토를 넘기거나 사용자에게 묻는다. 기능 버그가 보이면 보고하거나 `bugfix`로 전환한다. cleanup에 섞지 않는다.

## 이해 전달

마지막에 추적한 동작과 근거로 확인된 이유를 짧게 설명한다. 의도가 확인되지 않으면 모른다고 표시하고 지어내지 않는다. 생성한 흐름도나 요약은 살펴보기 쉽게 만들 수 있지만 팀이 공동 이해를 회복했다는 증거는 아니다. 사용자가 요청했거나 검증된 안정적인 결정을 기록할 때만 지속 문서를 만들거나 갱신한다.

## 중단 조건

요청된 감사에 근거 있는 우선순위 finding 과 분명한 범위 한계가 생겼거나, 요청된 범위 내 변경을 검증하면 끝낸다. 다음 조치가 미해결 제품 의도, 위험한 contract·아키텍처 선택, 근거 없는 가정에 달렸다면 범위를 넓히지 말고 필요한 결정을 정확히 보고한다.
